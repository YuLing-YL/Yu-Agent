# Yu-Agent 阶段汇报

> 基于 VLM 的 GUI 自动化智能体：让它自己看屏幕、点鼠标、敲键盘，把电脑上的重复操作做掉。
> 目标平台 macOS，优先跑本地模型（数据不出机器）。

**规模**：77 个 Python 文件 / 7108 行 / 15 次提交 / 57 个自动化测试全绿

---

## 一、这个项目在做什么

传统 RPA 靠坐标硬编码和控件 ID，界面一改就崩。这个项目换了个思路：
**让多模态大模型直接看截图，输出"点哪里、输入什么"，程序负责精确执行。**

一次任务的闭环：

```
截屏 → 枚举可交互元素并编号 → 连同截图喂给模型
     → 模型输出 {"type":"click","mark":38}
     → 按编号查表拿到精确坐标 → pyautogui 执行
     → 再截屏对比，确认动作是否生效 → 进入下一步
```

支持能力：打开应用、点击/输入/快捷键/拖拽、多步任务（自动拆子任务）、分层记忆（记住做过什么）、
停止保障（防无限点击）、图形化调试面板、评测集。

## 二、用到的工具（技术选型与理由）

| 层 | 工具 | 版本 | 用途 / 为什么选它 |
| --- | --- | --- | --- |
| 语言 | Python | 3.13.12 | 生态最全，pyobjc / 图像 / GUI 都成熟 |
| GUI | **PySide6** | 6.12 | 原生控件，后续可 PyInstaller 打包成 app |
| 模型接入 | **自研 OpenAI 兼容客户端** | — | requests 直调 REST，不依赖 openai SDK。一套代码同时支持本地 LM Studio / vLLM / 云端厂商 |
| 当前模型 | **qwen3-vl-A4B**（LM Studio 本地） | — | 视觉模型，本地推理，隐私可控、零调用成本 |
| 屏幕感知 | **macOS Accessibility API**（`pyobjc-framework-ApplicationServices`） | — | 唯一能拿到"控件语义"的官方途径：角色、标题、坐标、是否可用 |
| 窗口/前台 | **AppKit**（NSWorkspace / NSPasteboard） | — | 取前台应用、窗口列表；写系统剪贴板做中文输入 |
| 截屏 | **Quartz**（CoreGraphics） | — | 比 pyautogui 快且不触发截屏提示，性能 0.18s/帧 |
| 图像处理 | **Pillow** | 12.3 | 画 SOM 编号框、缩放、屏幕差分、感知哈希 |
| 鼠标键盘 | **pyautogui** | 0.9.54 | 跨平台成熟，但有两个坑后文会讲 |
| 配置 | **pydantic 2 + PyYAML** | — | 三层优先级：环境变量 > user.yaml > default.yaml；API Key 只落本地 |
| 存储 | **SQLite** | 内置 | 分层记忆持久化（情节/语义/程序/画像） |
| 评测 | **自研 eval/** | — | YAML 任务集 + 外部状态判据 + A/B 对比，不依赖第三方框架 |

### 为什么不用现成的 UI 自动化框架
- **Playwright / Selenium**：只能驱动浏览器，桌面应用（Finder、系统设置、终端）完全覆盖不到。
- **AppleScript**：需要每个应用单独写脚本，且没有"看"的能力，遇到自绘界面就废。
- **PyAutoGUI 纯坐标**：本地小模型估坐标误差几十像素，实测点偏。

结论：**用系统级 a11y 拿语义、用截图给模型看、用编号对齐两者**，是唯一能同时覆盖
「任意应用 + 模型自主决策」的路线。

```
├── gui/           1110 行   调试面板 + 置顶悬浮控制条
├── memory/         509 行   工作记忆 + 长期记忆（SQLite）
├── actions/        390 行   动作 schema + pyautogui 执行器
├── models/         348 行   OpenAI 兼容后端 + mock 后端
├── common/         242 行   日志、路径、图像工具
├── grounding/      204 行   动作解析、坐标还原、屏幕差分校验
├── skills/         187 行   技能注册表（可扩展的 Python 函数）
├── safety/         108 行   注入防护、危险动作拦截
└── prompts/         89 行   中英文提示词 + 加载器
```

### 主循环六阶段

| 阶段 | 做什么 | 对应文件 |
| --- | --- | --- |
| **observe** | 截屏 + 枚举元素 + 画编号框 | `perception/screenshot.py`、`a11y.py`、`som.py` |
| **recall** | 召回记忆 + 拼装运行期提示 | `memory/`、`agent/loop.py` |
| **think** | 调 VLM，产出下一步动作 | `agent/planner.py` |
| **ground** | JSON 解析 → 编号查表 / 坐标还原 → 语义校验 | `grounding/parser.py`、`agent/loop.py` |
| **act** | pyautogui 执行（中文走剪贴板） | `actions/executor.py` |
| **verify** | 再截屏比对，确认真的生效 | `grounding/verify.py` |

### 核心设计：Set-of-Mark（SOM）

不让模型自己估像素，"在图上画编号框，让模型报编号"：

```
a11y 枚举元素（角色/标题/坐标）
   → 用截图像素校准矩形（空框丢弃 / 过大的框收缩到内容）
   → 在截图上画 1、2、3… 红框
   → 编号表随消息一起给模型
   → 模型输出 {"type":"click","mark":38}
   → 查表得元素中心坐标 → 点击
```

实测对比：纯坐标模式下本地模型常偏几十像素；SOM 后点击落在元素中心，**准确率提升最明显的一处改动**。

SOM 的成败取决于**框画得准不准**——AX 报的矩形和眼睛看到的东西差很远
（详见坑 9），所以画框之前先做一层像素校准，这一步是编号能不能用的前提。

### 记忆系统：短期「我做过什么」+ 长期「提炼过的经验」

**短期（工作记忆）** —— 每个任务独立，任务结束即丢弃：

```
你已经做过的（最近的在上）：
  步骤3：按了 enter（Safari，18 个可点元素） → 屏幕没变化
  步骤2：输入「今天天气」（Safari，18 个可点元素） → 屏幕有变化
  步骤1：点击「搜索框」（WorkBuddy，30 个可点元素） → 屏幕有变化
⚠️ 上一步屏幕上没有任何变化 —— 换一种做法，不要重复它。
```

要点：动作要翻译成**人话**（「点了搜索框」，不是 `click(513,127)`）；
带上"屏幕变没变"；**倒序**让模型一眼看到上一步；子任务计划不在里重复
（由 `_build_subtask_hint` 单独强调，两处都写白占 token）。

**长期** —— SQLite 持久化，任务结束时**用模型做一次提炼**（纯文本、几百 token）：

| 产出 | 落到哪 | 用途 |
| --- | --- | --- |
| `summary` 做了什么、成没成 | 情节记忆 | 下次召回"上次干过类似的" |
| `lesson` 一条经验/教训 | 语义记忆 | 跨任务复用（"微信要先展开搜索框"） |
| `steps` 可复用步骤 | 程序记忆 | **仅成功任务**，失败路径不能当模板 |

召回时按「相关性 / 类型 / 新旧」排序，**知识优先于流水账**，总长限 700 字；
失败记录带 `[上次没成功]` 标记 —— 阻止模型照着重踩坑。

两个踩过的坑：
- **中文没有空格**，按空格分词等于整句去 LIKE，实测召回 0 条。改成中英分离 +
  2~3 字滑窗，并且**不做个数截断**（截断会把「天气」这种真正的关键词挤掉，
  留下的是 "Sa/af/用S" 碎片）。
- **旧蒸馏是占位实现**：`python -m yu_agent memory` 里能看到存的是
  「完成任务『打开微信』的方法已沉淀，共 2 步。」—— 零信息量。
  现在同一位置存的是「先点地址栏直接输入，旧内容会自动覆盖」这类可执行的经验。

## 四、踩过的坑与解决（重点）

### 1. 点击位置总偏一点 —— 模型估坐标不可靠

**现象**：点了之后落在目标左边/上面一点，偶发点空。
**根因**：VLM 直接输出像素坐标，本地 30B 级模型误差常在 20–60px。
**改法**：
- 上 SOM 编号（见上），模型只报编号；
- 模型若仍给坐标，用 `_snap_to_mark()` 在 45px 内**吸附**到最近的标记元素中心；
- 统一坐标系：截图缩回逻辑像素（Retina 2x 的坑），`scale_factor` 记录缩放比例用于还原。

### 2. 网页里的输入框永远识别不到 —— a11y 遍历把容器整棵子树跳过了

**现象**：浏览器地址栏/网页搜索框从来不在编号表里，模型只能瞎点。
**根因**：`_walk()` 遇到 `AXGroup / AXScrollArea / AXSplitGroup` 直接 `continue`，
而网页内容正好挂在这些容器下 —— 整棵子树被丢弃。
**改法**：容器**穿透遍历**（不再跳过），改为在末端用 `_useful()` 过滤噪声（整屏容器、分隔条、零尺寸）。
**验证**：修复后 `perceive` 自检能从 WorkBuddy 里列出 19 个应用元素（含「下拉框 | 搜索设置项」
这类真实输入框），修复前只枚举到少数几个、且完全没有输入框。

### 3. Finder 里一行行都是"无名单元格" —— 名字不在元素自己身上

**现象**：编号表里 #23~#37 全是「单元格」「行」，模型分不清哪个是 `code`，对同一坐标连点 3 次。
**根因**（真机 AX 树验证）：`AXRow` / `AXCell` 自身的 `AXTitle / AXDescription / AXValue` **全为空**，
文件名在子元素 `AXStaticText` 的 `AXValue` 里。
**改法**（做成通用规则，不针对 Finder）：
- 名称回退链：`AXTitle → AXDescription → AXValue → AXPlaceholderValue → AXHelp`；
- 元素没名字时，从**子元素**里挖 ≤60 字的短文本（覆盖 AppKit 列表 / Electron 列表 / 网页表格 / Qt 表格）；
- 同矩形"套娃"（行 → 单元格 → 文字）只保留最值得点的一个；
- 无标签图标每应用限流 8 个（否则工具栏图标会淹没编号表）；
- 不用 `AXRoleDescription` 兜底 —— 它只是角色名（"图像"），会造出一堆同名条目，比没名字更误导。

### 4. 编号跨帧漂移 —— 模型记住编号，编号却换了主人

**现象**：4 步全是 `click mark=38`，但 reason 依次说 iCloud云盘 / yuling / yuling，
实际点到了别的地方。
**根因**：编号原来**每帧按坐标重排**。第 1 帧 `#38` 是「iCloud云盘」，第 2 帧同一编号落到了「yuling」，
模型跨帧引用就失效。
**改法**：新增 `MarkStabilizer`，按 `(应用, 角色, 名字, 位置/16px)` 认元素身份，跨帧复用同一编号；
列表滚动用"同名 + 160px 内"模糊匹配兜底。
**验证**：同一画面连采 3 帧，**19/19 个编号指向同一元素**。
**配套**：`_verify_mark_semantics()` —— 模型说要点「yuling」却给了「iCloud云盘」的编号时，
按 reason 里出现的名字找唯一匹配自动纠正，日志和界面都会写「编号纠正」。

### 5. 中文一个字都打不进去 —— pyautogui 不支持非 ASCII

**现象**：动作执行"成功"，屏幕上却什么都没输入。
**根因**：pyautogui 的按键表里**没有任何非 ASCII 字符**，`keyDown("今")` 被静默 return ——
最坑的是它不报错，任务看起来"成功"了。
**改法**：含非 ASCII 的文本走「写系统剪贴板 + ⌘V 粘贴」，粘贴后**还原用户原剪贴板**；
纯 ASCII 仍用 `write()` 逐字输入（速度可配 `agent.type_interval_s`）。
**顺带修的同类问题**：按键别名 `cmd` / `control` 不在 pyautogui 合法键表里（只有 `command` / `ctrl`），
模型写 `cmd+l` 会退化成只按 `l`。现在统一规范化，且**非法键直接抛错**，不再无声失败。

### 6. 任务完成后不停 / 点了停止还继续点

**现象**：任务其实完成了，模型还在反复点；点「停止」后仍会多执行一步。
**根因**（4 个）：
1. 重复检测只看"连续且完全相同"，A→B→A→B 绕圈或坐标抖动几像素就躲过；
2. 签名用原始坐标未量化；
3. `while` 只在循环顶部检查停止，而一次模型推理要 10–30s，返回后的动作照样执行；
4. 子任务游标从未推进，模型永远看到"当前子任务 1"。
**改法**（多层兜底 + 语义区分）：
- 坐标按 **20px 网格量化**，同一目标**累计**操作超限即停（拦绕圈）；
- 点击总预算、屏幕连续无变化、步数上限、重复拆分上限；
- **停止三处检查**：模型返回后、坐标解析后、执行动作前，命中即丢弃动作；
- 区分停止语义：重复/无变化 → 判定"大概率已完成"；点击超预算 → 判定"异常"；
- 新增**置顶悬浮控制条**（跨桌面/全屏可见），任务跑起来后随时能停。

### 7. "假成功"：点了几次搜索框，一个字没输入，却显示完成

**现象**：日志显示 ✅ 完成，实际什么都没搜。
**根因**：① 模型点输入框后不输出 `type`，反复点同一个框；② 终止逻辑把"重复点击 + 屏幕无变化"
一律判为"已完成"。
**改法**：
- **输入看护**：点击的元素若是输入类，该步结果标注「输入框已聚焦，下一步必须 type」，
  下一轮提示词强提示"不要再点这个输入框"；
- 修正判定：**重复操作但屏幕每次有变化** → 视为已完成；**重复且屏幕始终没变化** → 判未完成，不谎报成功；
- 提示词加「输入三步」：click 聚焦 → type 输入 → key+enter 提交，并硬性规定"没执行过 type 不许 done"。

### 8. 说"我看不到你的屏幕"，然后一句话不干

**现象**：输入「你能看到我的屏幕吗」，模型回一句"我看不到你的屏幕哦"，任务结束，0 步。
**根因**：GUI 在启动主循环前有一道**意图识别**（判断要不要操作屏幕），但那次请求
**只发文字、不带截图**。模型手里没图，回答"看不到"完全正确；错的是把这句话当成"不需要操作屏幕"。
**改法**：
- 硬规则：输入含**屏幕/桌面/界面/窗口/截图/看**这类词 → **强制**执行，覆盖模型判断；
- 强制执行时把"我看不到"这类回复换成"好的，我先截屏看一下当前界面"，避免界面文案自相矛盾；
- 提示词新增 **Look-only 任务**模式：看看类任务不点击，直接用一条 `done` 把看到的内容写进 `reason`。
**验证**：现在 1 步完成，`reason` 准确描述"WorkBuddy 窗口 / 访达 / 北京 14°C 天气挂件 / 系统时间"。

### 9. 编号框比元素大、互相重叠、还有一堆罩在空白上

**现象**：标注图（`runs/20261019-212505/step_01.png`）里，侧边栏每行的框高是文字的
2~4 倍，相邻框压在一起；聊天列表整行宽的框一个叠一个；还有十几个框悬在纯白区域上，
里面什么都没有。模型在一堆重叠的框里选编号，必然选错。

**根因**（三层，逐层查出来的）：
1. **AX 报的矩形是"布局盒子"，不是"眼睛看到的东西"**。`AXRow` / `AXCell` 的 rect
   含 padding，甚至含整块滚动可视区；`AXGroup` 常常报整行宽。画出来就是巨大框。
2. **AX 会报已经不可见的元素**。自绘界面（微信 / Electron）滚动过的行仍报旧坐标；
   未渲染的面板、被隐藏的 tab 也报。这些框落在屏幕上就是空白。
3. **标签字号跟着元素高度缩**。列表行只有 20px 高时标签跟着变 14px，一排标签
   紧挨着写，图上成了"11|12|13"这种读不出边界的串。

**改法**（全部通用，不针对任何 App）：
- 新增 `perception/content.py`：**用截图像素反过来校准 AX 的矩形**。对每个元素框
  做梯度分析，逐行/逐列统计"强边缘像素个数"，取首尾得到内容真实外接框。
  - 框比内容大 → **收缩到内容**（列表行从 80px 收到 20px，不再压邻居）；
  - 框里没有内容 → **丢弃**（这就是那些罩在空白处的大红框）。
  - 用"计数"而不是"均值"是关键：600px 宽的聊天行里文字只占左边 60px，
    取均值会被右边的纯白稀释成 0，把有内容的行误判成空框（实测踩过）。
  - 1px 分隔线在每列只贡献 2 个边缘，阈值取 3 就不会把整行宽度拉满。
- `a11y.py`：元素必须落在**自己应用某个窗口**里，离所有窗口都超过 160px 才判为
  幽灵元素丢弃；同时加"丢太多就作废规则"的兜底（实测一刀切会一次误杀 37 个元素）。
- `som.py`：标签字号**固定**（不随元素高度缩）+ 标签之间留 2px 禁入区，
  密集按钮上也能读出"11 12 13"而不是糊成一团。
- **帧可信度**：统计"框落在有画面的位置"的比例。低于 50% 说明截图和元素枚举
  不是同一时刻/同一桌面（切了 Space、刚唤醒、截屏被卡住 30s），
  这时**自动降级**为"看画面直接给坐标"，不再让模型照着错位的编号点。

**验证**：同一张真实截图，`perceive` 输出从「0 个空框 / 0 个收缩」变成
「丢弃空框 6 个 / 收缩到内容 31 个」；`帧可信度 0.86`。合成场景对比图见
`runs/marks_before_after.png`。回归测试 `tests/test_content_marks.py`（10 项）。

**顺带补的第二条路**：如果用户/模型更想"给原图自己算坐标"，`coords` / `off` 模式
已可用，并加了**语义锚定**兜底：模型估的像素点若附近没有元素，但它 `reason` 里
说清了目标名字且编号表里有同名元素（≤220px），就用元素精确坐标替代。

### 10. 搜索框里旧词没删，新词直接拼在后面 → 搜索结果全错

**现象**：「帮我搜一下今天天气」，agent 点了搜索框、打了「今天天气」、回车，
结果搜出来的是「昨天的词今天天气」。框里的旧内容一个字都没删。

**先分清是"模型没让它删"还是"让它删了但没执行"**——查运行轨迹（runs/*/trace.jsonl）
就能确定：所有搜索任务的动作序列都是

```
step1 click 搜索框   →  step2 type "今天天气"  →  step3 key enter
```

**模型从头到尾没输出过任何清空动作**（没有 cmd+a，也没有 backspace）。所以不是执行丢失，
是模型根本没意识到「框里可能已经有内容」。

**改法（两层）**：
1. **执行层兜底**：`type` 动作新增 `replace` 语义（先 ⌘A 全选再输入）。
   `loop` 在「上一步点的是**单行**输入框」时自动打开它 —— 搜索框/地址栏里输入新内容，
   语义几乎总是替换。**多行文本域不自动覆盖**（往文档里写正文不能把用户已有内容删掉）。
2. **提示词说清**：明确告诉模型「框里已有旧内容就直接 type，系统会覆盖，
   不要自己发一串 cmd+a / backspace」—— 否则模型要么漏删，要么用 3~4 步去删还删不干净。

**验证**：`tests/test_input_replace.py`（6 项），覆盖解析层（顶层 `replace` 也要收）、
执行层（⌘A 顺序、字符串 `"true"` 也认）、loop 层（搜索框自动覆盖 / 文本域不覆盖）。

### 11. 想打开的应用不在屏幕上，agent 就在屏幕上反复找

**现象**：任务要打开「剪映」，它不在编号表里，agent 就点 Dock、翻访达、滚列表，
折腾十几步也没打开。

**根因**：提示词只说了「优先用 open_app」，但没说**判断标准**（什么情况下该判定
"屏幕上找不到，直接去打开"），也没给 open_app 失败之后的第二选择。

**改法**：
- `open_app` 内部做成**四级查找**：`open -a 应用名` → 扫应用程序目录找 `.app` 再 open →
  Spotlight 索引（`mdfind`）→ AppleScript activate。实机验证：「微信」用 `open -a` 和目录
  扫描都找不到，靠 mdfind 命中 `/Applications/WeChat.app` —— 正是之前失败的那类场景。
- 新增 `spotlight_search` 技能：⌘+空格 → 输入名字 → 回车。**先检查 Spotlight 窗口真的
  弹出来了才敲键盘**，弹不出来按 Esc 取消并如实说明（盲敲会把字打进用户当前文档里）。
- 提示词加判断标准：「目标应用的窗口/按钮如果不在编号表里、截图上也看不到，
  就不要在屏幕上找，直接 open_app」，并写明三条路的先后顺序。

## 五、走过的弯路（这几条比成功经验更有用）

**1. 想"运行前隐藏其它应用来减少干扰" —— macOS 不允许，整块删掉**
试过 5 种接口：`NSRunningApplication.hide()` 从后台进程调返回 NO；
`AXMinimize` 返回 -25205 不支持；写 `AXMinimized` 返回 0 但不生效；
AppleScript 控制其它应用报 -10004；`activateWithOptions_` 返回 True 但前台没变（防抢焦点）。
辅助功能权限是正常的（`AXIsProcessTrusted()=True`），所以不是权限问题，是系统限制。
**结论**：这个功能在 macOS 上不成立。改成**纯感知侧的降噪**（只标最前面的应用 + 程序坞），
不碰用户任何窗口 —— 效果一样，且不依赖权限。

**2. 第一版 GUI 花了时间做深色主题，对成功率零帮助**
圆角卡片、hover、自绘滚动条写了 265 行，但排查问题时真正需要的是
"模型看到的是哪张图、它原话说了什么、编号表长什么样"。
后来整块删掉，改成**调试面板**：左侧是模型实际收到的标注图，右侧是编号表 + 模型原始输出 + 执行日志，
并支持**单步执行**（跑一步、看清楚、再放行）。这才是能提速的东西。

**3. 调参之前先确认"指标本身可信"**
一开始想用 `state.success` 当评测指标，后来发现它本身就含"重复点击 = 已完成"的兜底，
会虚报成功 —— 等于让被测对象自己改考卷。
所以评测集的判据全部改成**读外部状态**（前台应用 / 窗口标题 / 文件系统），
并区分「通过 / 未通过 / 待人工 / 无效起点（起点已满足终点，不计分）」。

**4. 提示词改英文：能做，但别指望它是银弹**
英文提示词的字符更多，token 通常相当；真正的收益在 JSON 约束和指令遵循更稳。
所以做成可切换（`prompts.language: en/zh`），建议用评测集 A/B，而不是拍脑袋。

## 八、已知限制

1. **Electron / Canvas 类应用**（WorkBuddy、Obsidian）a11y 只暴露个位数元素，
   截图上有内容但编号表几乎是空的。→ 待接 OCR 兜底。
2. **本地模型长任务稳定性**：10 步以上的任务容易忘记目标，需要靠提示词和终止保障兜住。
3. **系统级限制**：后台进程无法隐藏/激活其它应用的窗口（见弯路 1）。
4. **静态评测样本偏少**：10 任务 × 3 次只能看大方向，10pt 以内的差异还分不清。
5. **屏幕锁定/休眠时** Quartz 截屏会被阻塞（实测可达 30s），已加超时告警。

## 附：汇报节奏建议（约 10 分钟）

1. **一句话定位**（30 秒）：传统 RPA 靠坐标硬编码，界面一改就废；这个项目让 VLM 直接看屏幕决策，
   程序负责精确执行。
2. **技术选型的一句话理由**（1 分钟）：a11y 拿语义、截图给模型看、SOM 编号把两者对齐 ——
   这是能同时覆盖"任意桌面应用 + 模型自主决策"的唯一组合。
3. **主循环**（1 分钟）：observe → think → ground → act → verify，重点讲 verify 和终止保障。
4. **三个最硬的坑**（4 分钟，挑着讲）：
   - 编号跨帧漂移（模型记住 #38，下一帧 #38 换了元素）→ 稳定器，19/19 验证
   - 中文打不进去（pyautogui 静默失败）→ 剪贴板粘贴
   - 假成功 / 停不下来 → 多层终止 + 停止三处检查
5. **弯路**（1.5 分钟）：隐藏窗口受 macOS 限制整块删掉、GUI 美化改成调试面板 ——
   说明"验证过不行就砍"的判断过程。
6. **数据 + 下一步**（1.5 分钟）：57 个测试、编号稳定性 19/19、OCR 0.33s 待接。

**最容易被追问的三个问题，答案在正文**：
- *为什么不让模型直接给坐标？* → 第四节第 1 条（本地模型误差 20–60px，SOM 后落在元素中心）
- *怎么保证它不停地点？* → 第四节第 6 条（五层兜底 + 停止三处检查）
- *怎么知道它真的做成了？* → 第五节第 3 条 + 第七节（判据读外部状态，不采信模型自报）
